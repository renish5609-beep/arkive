# Arkive

Arkive is an open-source computational public-history framework for reconstructing communities from fragmented archival records while preserving the evidence, uncertainty, and source provenance behind every connection.

## Projects

- **Project 001 — Quakertown Reconstructed**, Denton, Texas. The flagship reconstruction. It currently holds 5 people, 5 place records, 6 sources, and 6 relationships. Most sources are short descriptions, and transcripts have not yet been read in full.
- **Project 002 — Freedmen's Town Reconstructed**, Houston, Texas. A small portability pilot, built to prove that the same framework can reconstruct a second, independent community without rewriting the application. It currently holds 0 people, 4 places, and 3 sources.

Start at [/projects](/projects), or the [guided demo](/demo).

## Why this exists

Archival records about a community are scattered across oral histories, government files, maps, and photographs. Each one holds part of the story, and none holds all of it. Historians often reconstruct these connections by hand and keep the reasoning in notes that others cannot easily check. Arkive keeps the reasoning in the data itself, so a claim can be traced back to its source and its uncertainty is visible. It is built to do this for more than one community, with the same code.

## How it works

```
archival source -> raw mention -> structured evidence -> possible entity match
  -> human review -> canonical historical record -> map / relationship graph / export
```

- A **project** is one reconstruction (Quakertown, Freedmen's Town, or a future one). Each has its own manifest, sources, records, mentions, spatial evidence, and research queue. IDs only need to be unique within their own project.
- A **mention** is one occurrence of a name, place, or institution in a source.
- A **match candidate** is a proposal that two mentions may refer to the same entity. It is generated by fixed rules, and it stays pending until a person reviews it.
- A **canonical record** is a person, place, or relationship that a source supports. Only reviewed links become canonical.

Automated match scores are heuristics that prioritize research. They are not historical proof, and they never merge records on their own.

## Current capabilities

- **Map:** an interactive OpenStreetMap view, per project. Exact and approximate locations are drawn with different marker styles. Unresolved places are listed in text, not drawn. A project with no mappable places shows an explanatory empty state instead of a blank map.
- **Archive:** searchable records, filterable by verification state, archival mentions, and open research questions.
- **Provenance:** every source has its own page, with links to the original archive where one exists.
- **Entity resolution:** deterministic candidate matches with the reasons for and against each one, reviewed at `/projects/<slug>/review`.
- **Exports:** the full dataset as JSON, and CSV for people, places, relationships, mentions, and sources, per project. Source IDs are preserved.
- **Validation:** every project is checked for broken references, duplicate IDs, impossible coordinates, inconsistent review decisions, and a valid manifest. Project slugs and numbers cannot collide with each other.

## Research principles

- **No invented coordinates.** A location is shown only when its evidence supports it. A modern street name is not evidence of a historical location, and a street-bounded boundary description does not justify an arbitrary centroid.
- **Human review.** Automated suggestions stay pending until a person checks them against the sources.
- **Uncertainty is preserved.** Open questions are recorded in a research queue rather than resolved by guessing.
- **Provenance on every claim.** Records cite the sources that support them.
- **Projects stay separate.** Evidence never transfers automatically between projects. The same historical person appearing in two projects remains two separate records until an explicit cross-project linkage model exists.

See the [methodology](/about), the [provenance policy](docs/provenance-policy.md), and the [data dictionary](docs/data-dictionary.md).

## Run locally

Requirements: Node.js 20 or later and npm.

```bash
npm install
npm run dev
```

Then open http://localhost:3000.

No environment variables are required for local development. Set `NEXT_PUBLIC_SITE_URL` only when you have a production URL for metadata. See [docs/deployment.md](docs/deployment.md).

## The project directory contract

Every project lives at `data/projects/<slug>/` and must contain exactly these files:

```
project.json
people.json
places.json
sources.json
relationships.json
location-evidence.json
georeference-queue.json
mentions.json
match-candidates.json
research-queue.json
```

Projects are discovered from this directory at runtime. Adding a project never requires editing a registry or any application source file.

### Scaffold a new project

```bash
npm run create:project -- --slug example-town --number 003 --title "Example Town Reconstructed" --location "Example, Texas"
```

This refuses an existing directory, an existing slug, or a duplicate project number. It creates every required file, with the data files empty and the manifest filled with placeholder text clearly marked for editing. It never invents historical content. See `docs/project-template/` for an annotated example of each file.

### See every project

```bash
npm run projects:status
```

## Data validation

Run these after changing any file under `data/projects/`:

```bash
npm run validate:data
npm run audit:provenance
npm run research:status
npm run georef:status
npm run review:status
npm run matches:preview
npm run matches:write
```

All of these run across every project by default. Scope any of them to one project with `-- --project <slug>`, for example:

```bash
npm run validate:data -- --project quakertown
npm run validate:project -- --project freedmens-town
```

- `validate:data` (and its alias `validate:project`) checks structure, references, coordinates, review consistency, and the project manifest. It exits nonzero on errors. IDs are only ever compared within their own project, so a Quakertown record cannot accidentally reference a Freedmen's Town entity, or the reverse.
- `audit:provenance` fails when a canonical record has no source. It warns about thin evidence.
- `matches:preview` shows candidate matches without changing any file; it runs across every project by default. `matches:write` saves them and always requires an explicit `--project <slug>` — it never writes match candidates across every project by default. Neither ever overwrites an accepted or rejected decision.
- `add:mention` adds one archival mention to one project and always requires `--project <slug>`.

Before a release, run:

```bash
npm run check:release
```

This runs validation, the provenance audit, the status reports, lint, build, and the release audit. It is non-interactive.

To check whether source links still work, run:

```bash
npm run check:links
```

This reports healthy, redirected, broken, and unreachable links, grouped by project. It does not change any data, and network problems do not fail the release.

## Dataset export

- `GET /api/export/<slug>?format=json` returns project metadata, people, places, relationships, sources, mentions, match candidates, and location evidence for that project.
- `GET /api/export/<slug>?format=csv&entity=people` (also `places`, `relationships`, `mentions`, `sources`) returns a CSV with headers. Array fields are joined with semicolons.
- `GET /api/projects/<slug>` returns a compact machine-readable summary for that project, including counts, the verification model, and export URLs.

Exports keep source IDs and verification metadata, so downstream users can audit where each claim came from.

## External validation

External reviews and outreach are recorded only after they happen. Run these after any change to `data/external-reviews.json`, `data/project-impact.json`, or `data/outreach-log.json`:

```bash
npm run outreach:status
npm run review:status
npm run audit:impact
npm run metrics:generate
```

- `review:status` fails on malformed review records.
- `audit:impact` fails when a count is larger than its recorded evidence.
- `metrics:generate` rewrites `docs/application-metrics.md` from the data. Unknown values are shown as Not yet measured.

See [docs/external-review-workflow.md](docs/external-review-workflow.md) and [docs/impact-thresholds.md](docs/impact-thresholds.md).
