# Arkive

Arkive is an open-source computational public-history platform. It reconstructs communities from fragmented archival records while preserving the evidence, uncertainty, and source provenance behind every connection.

## Quakertown Reconstructed

The first case study reconstructs Denton, Texas's historic Black Quakertown community and the displacement of its residents during the 1920s. It connects people, homes, schools, and relationships to the archival sources that document them, and it shows where the evidence is still incomplete.

The reconstruction is early. It currently holds 5 people, 5 place records, 6 sources, and 6 relationships. Most sources are short descriptions, and transcripts have not yet been read in full. Coverage is limited to what the sources support.

Start with the [Quakertown project page](/projects/quakertown), or the [guided demo](/demo).

## Why this exists

Archival records about a community are scattered across oral histories, government files, maps, and photographs. Each one holds part of the story, and none holds all of it. Historians often reconstruct these connections by hand and keep the reasoning in notes that others cannot easily check. Arkive keeps the reasoning in the data itself, so a claim can be traced back to its source and its uncertainty is visible.

## How it works

```
archival source -> raw mention -> structured evidence -> possible entity match
  -> human review -> canonical historical record -> map / relationship graph / export
```

- A **mention** is one occurrence of a name, place, or institution in a source.
- A **match candidate** is a proposal that two mentions may refer to the same entity. It is generated by fixed rules, and it stays pending until a person reviews it.
- A **canonical record** is a person, place, or relationship that a source supports. Only reviewed links become canonical.

Automated match scores are heuristics that prioritize research. They are not historical proof, and they never merge records on their own.

## Current capabilities

- **Map:** an interactive OpenStreetMap view. Exact and approximate locations are drawn with different marker styles. Unresolved places are listed in text, not drawn.
- **Archive:** searchable records, filterable by verification state, archival mentions, and open research questions.
- **Provenance:** every source has its own page, with links to the original archive where one exists.
- **Entity resolution:** deterministic candidate matches with the reasons for and against each one, reviewed at `/review`.
- **Exports:** the full dataset as JSON, and CSV for people, places, relationships, mentions, and sources. Source IDs are preserved.
- **Validation:** the dataset is checked for broken references, duplicate IDs, impossible coordinates, and inconsistent review decisions.

## Research principles

- **No invented coordinates.** A location is shown only when its evidence supports it. A modern street name is not evidence of a historical location.
- **Human review.** Automated suggestions stay pending until a person checks them against the sources.
- **Uncertainty is preserved.** Open questions are recorded in a research queue rather than resolved by guessing.
- **Provenance on every claim.** Records cite the sources that support them.

See the [methodology](/about), the [provenance policy](docs/provenance-policy.md), and the [data dictionary](docs/data-dictionary.md).

## Run locally

Requirements: Node.js 20 or later and npm.

```bash
npm install
npm run dev
```

Then open http://localhost:3000.

No environment variables are required for local development. Set `NEXT_PUBLIC_SITE_URL` only when you have a production URL for metadata. See [docs/deployment.md](docs/deployment.md).

## Data validation

Run these after changing any file in `data/projects/quakertown/`:

```bash
npm run validate:data
npm run audit:provenance
npm run research:status
npm run georef:status
npm run review:status
npm run matches:preview
npm run matches:write
```

- `validate:data` checks structure, references, coordinates, and review consistency. It exits nonzero on errors.
- `audit:provenance` fails when a canonical record has no source. It warns about thin evidence.
- `matches:preview` shows candidate matches without changing any file. `matches:write` saves them, and it never overwrites an accepted or rejected decision.

Before a release, run:

```bash
npm run check:release
```

This runs validation, the provenance audit, the status reports, lint, build, and the release audit. It is non-interactive.

To check whether source links still work, run:

```bash
npm run check:links
```

This reports healthy, redirected, broken, and unreachable links. It does not change any data, and network problems do not fail the release.

## Dataset export

- `GET /api/export/quakertown?format=json` returns project metadata, people, places, relationships, sources, mentions, match candidates, and location evidence.
- `GET /api/export/quakertown?format=csv&entity=people` (also `places`, `relationships`, `mentions`, `sources`) returns a CSV with headers. Array fields are joined with semicolons.
- `GET /api/projects/quakertown` returns a compact machine-readable summary, including counts, the verification model, and export URLs.

Exports keep source IDs and verification metadata, so downstream users can audit where each claim came from.
